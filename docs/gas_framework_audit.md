# GAS audit and project rules

This is the research record for the Godot GAS port. Follow [the current authoring workflow](ability_system.md) for implemented features. Consult [Tranek's reference](https://github.com/tranek/GASDocumentation/blob/master/README.md) first, then the local Lyra source and installed Unreal GameplayAbilities plugin. The Unreal RPG is the reference for this game's effect assets and gameplay. The Godot implementation targets single player.

## Evidence and limits

The counted corpus contains **483 concrete authored Unreal GAS configurations**, comprising **173 Gameplay Ability and 310 Gameplay Effect Blueprints** across 13 public projects. We downloaded 576 commit-pinned Unreal packages and decoded their generated classes, class default objects, effect component data and available compiled Blueprint operations using [UAssetAPI](https://github.com/atenfyr/UAssetAPI). We retained 549 with readable behavioral evidence beyond filenames, tags used solely as labels, and presentation metadata. We collapsed 14 identical normalized evidence records, excluded 28 records from a closely related tutorial, and grouped 18 sibling OpenPF2 BoostRuleOptions variants as one. The final ancestry check excluded seven Actor classes with ability or effect naming prefixes. Multiple assets can use the same mechanism. Static inspection establishes serialized behavior and graph operations, while inheritance or runtime conditions can change how a particular activation behaves.

## Patterns and decisions

| Pattern | Verified example | Project rule |
| --- | --- | --- |
| Input or AI requests an action | Lyra grants Jump and sends the jump request to Character Movement. Its held aim ability cleans up on input release. | Grant Sprint, Jump, Crouch, Fireball and attacks normally. Input is a request to the ASC. An execution owns the action lifetime and delegates physical work. [Lyra abilities](https://dev.epicgames.com/documentation/unreal-engine/abilities-in-lyra-in-unreal-engine) |
| A gameplay condition requests an action | Lyra's health logic reports death as a gameplay event and its Death ability owns the response. UE5ActionRPG reports a Fire Buildup threshold, and the event-triggered Burning ability commits its authored activation effects. | Publish condition changes through the receiving actor's gameplay event dispatcher. The grant declares the activation event and the running execution owns the response. [Lyra health source](https://github.com/BulkheadLtd/Lyra_5_4/blob/db8015cccd495fac10c863825c54c0a2914878a0/Source/LyraGame/Character/LyraHealthComponent.cpp#L148-L166) · [Burning trigger](https://github.com/ilchul1/UE5ActionRPG/blob/9d5f4eb691550c8feb7e94e81c07f956b65374dc/Source/UE5ActionRPG/Character/PTCharacter.cpp#L851-L892) · [Burning ability](https://github.com/ilchul1/UE5ActionRPG/blob/9d5f4eb691550c8feb7e94e81c07f956b65374dc/Source/UE5ActionRPG/AbilitySystem/Abilities/PTGameplayAbility_Burning.cpp) |

## Current gaps

- The ASC still contains weapon-specific source compatibility for isolated formula fixtures. The playable prototype uses direct grants. When actual equipment is designed, move its delivery compatibility rules to the relevant source or execution boundary.
- Godot uses GDScript tasks and execution resources for gameplay logic. Editor authoring happens through exported data on ability and effect resources. The framework provides the tasks, application policies, effect components and cue routes documented in the authoring guide. Consult installed Unreal source before expanding an API or assuming identical semantics for an Unreal-only task or component option.

## Encumbered migration

The installed UE 5.8 source places `AbilityTriggers` on `UGameplayAbility` to declare what activates it. `HandleGameplayEvent` uses the incoming tag and its ancestors to find activation triggers, then delivers event callbacks. A running ability can use `WaitGameplayEvent` and call `EndAbility` from its callback when that fits its execution. Keep that distinction in Godot. The ability definition authors the activation event, and the execution decides how to respond to later events and when to finish. [UE trigger types](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/GameplayAbilities/EGameplayAbilityTriggerSource__T-) · [Wait Gameplay Event](https://dev.epicgames.com/documentation/unreal-engine/BlueprintAPI/Ability/Tasks/WaitGameplayEvent) · [EndAbility](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/GameplayAbilities/UGameplayAbility/EndAbility)

1. **Report the condition.** The saved player authors an `AttributeGameplayEventRule` under Attributes. It compares final Carried Weight and Carry Capacity. Strictly above capacity sends `Event.Carry.Overloaded`. Returning to or below capacity sends `Event.Carry.WithinCapacity`. The rule reports facts independently of the ability and its effect.
2. **Activate and listen.** Encumbered is granted alongside the actor's other actions, with `Event.Carry.Overloaded` as its activation trigger. Its active `MaintainEffectExecution` listens for `Event.Carry.WithinCapacity` and calls `cast.finish()`. Other gameplay event producers and executions use the same dispatcher. [Godot gameplay event authoring](ability_system.md#gameplay-events)
3. **Own the effect through the activation.** `MaintainEffectExecution` stores its own indefinite effect handle in `AbilityCast.data`, removes the exact instance when its activation ends and restores it if cleared while the activation remains active. It removes a just-applied handle if a synchronous callback ended the cast before that handle returned.
4. **Consume the output.** The effect grants only `State.Encumbered` and supplies the debuff icon. Sprint keeps the state in its Blocked Tags and Interruption Tags. Movement supplies live speed and jump factors. F3 and the HUD observe the results, and F1 omits status activations from combat statistics.
